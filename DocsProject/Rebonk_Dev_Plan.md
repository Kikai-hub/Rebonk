# Rebonk — План разработки для Claude Code

Этот план построен на основе `Rebonk_GDD.md`. Идти строго по этапам — каждый следующий этап опирается на рабочий результат предыдущего. Внутри этапа пункты можно переставлять местами, но не перескакивать через этапы целиком: сначала должен быть играбельный вертикальный срез, потом — расширение контента и полировка.

Формат каждого этапа: **Цель → Задачи → Критерий готовности (Definition of Done)**. Этап считается закрытым, только когда критерий готовности выполнен и билд собирается/играется без критичных багов.

## Этап 0 — Инициализация проекта

**Цель:** Рабочий пустой проект с правильной конфигурацией под мобильный ландшафтный 2D-проект.

**Задачи:**
- Создать проект Unity 6.5 (6000.5.2f1), 2D (URP) template
- Настроить Player Settings: ориентация экрана — Landscape Left/Right (запретить Portrait), таргет-платформы iOS + Android
- Настроить Build Settings под Android и iOS (даже без реального билда на устройство на этом этапе)
- Продумать и создать структуру папок проекта (Scripts, Prefabs, Art, Audio, ScriptableObjects, Scenes и т.д.) — зафиксировать конвенцию именования
- Настроить систему контроля версий (.gitignore под Unity)
- Настроить базовый пайплайн для пиксель-арта: Pixel Perfect Camera (пакет), настройки импорта спрайтов (Point filter, сжатие под мобильные)

**Definition of Done:** Пустой проект открывается, собирается в тестовый билд под Android без ошибок, камера и разрешение экрана корректно ведут себя в ландшафтной ориентации.

## Этап 1 — Вертикальный срез: движение + один вид оружия + враги

**Цель:** Минимальный играбельный цикл на одной сцене без UI-полировки — только чтобы механика "работает и это весело".

**Задачи:**
- Player controller: движение по виртуальному джойстику (реализовать джойстик как переиспользуемый UI-компонент)
- Камера следует за игроком
- Один тестовый персонаж (плейсхолдер-спрайт допустим) со статами: HP, скорость, урон
- Один вид оружия (например, melee-арка) с авто-таргетингом ближайшего врага
- Простой спавнер врагов: один тип врага, спавн по таймеру по периметру вне экрана, движение к игроку
- Урон при контакте враг↔игрок, смерть врага при обнулении HP
- Базовый object pooling для врагов сразу (не откладывать оптимизацию на потом — тут закладывается архитектурный паттерн для всего проекта)

**Definition of Done:** Можно запустить сцену, водить персонажа джойстиком, оружие автоматически бьёт врагов, враги умирают, спавнятся новые.

## Этап 2 — Прогрессия внутри забега (XP, левел-ап, апгрейды)

**Цель:** Замкнуть базовый roguelite-цикл: убийства → опыт → выбор апгрейда → усиление.

**Задачи:**
- Гемы опыта, дропающиеся с врагов, с притягиванием в радиусе подбора (магнит)
- Система уровня персонажа и кривая необходимого опыта для левел-апа
- UI экрана левел-апа: пауза игры, показ 3–4 случайных карточек апгрейда
- ScriptableObject-архитектура для описания апгрейдов (оружие/пассивка) — чтобы дальше легко добавлять контент без правки кода
- Добавить минимум 2–3 вида оружия и 2–3 пассивных предмета для проверки системы выбора и балансировки
- Лимит слотов оружия/предметов (зафиксировать число, например 6+6)

**Definition of Done:** Полный цикл "играю → леплюсь → выбираю апгрейд → игра продолжается с учётом апгрейда" работает без крашей, апгрейды реально влияют на статы/поведение оружия.

## Этап 3 — Таймер зоны, фаза выживания и враги-духи

> **Пересмотрено 2026-09-19.** Первая реализация делала фазу духов 60-секундным отсчётом, после которого зона считалась пройденной. Это неверно: фаза духов — бессрочное выживание, а переход дальше даёт только портал убитого босса (этап 6). Код этапа 3 приведён в соответствие (см. «Статус» ниже).

**Цель:** Реализовать структуру одного уровня (10–12 минут + бессрочная фаза выживания с духами) согласно GDD.

**Задачи:**
- Таймер зоны на 10–12 минут, видимый в HUD
- По истечении таймера — переход в фазу выживания (обычный спавн прекращается)
- Спавн врагов-духов на фазе выживания: волны со всех сторон экрана
- Механика нарастающей силы духов **по секундам** фазы (не по волнам, а от прошедшего времени внутри фазы — модификатор статов, растущий по формуле от времени), **без верхней границы по времени**
- Фаза выживания **сама не заканчивается**; в HUD показывается время выживания (растёт вверх), оно фиксируется как результат забега
- Точка входа для перехода на следующий уровень (`ZoneTimer.CompleteZone()`), которую вызовет портал убитого босса на этапе 6. До этапа 6 перехода нет (пока можно вызывать вручную для тестов)

**Definition of Done:** Игрок доживает таймер → начинается заметно отличающаяся фаза с духами, которая не заканчивается; духи ощутимо усиливаются с каждой секундой; в HUD виден счётчик времени выживания; переход на следующий уровень возможен только через вызов `CompleteZone()` (позже — портал).

**Статус:** реализовано и приведено к схеме выживания 2026-09-19 (переход по завершении фазы удалён).

**Цель:** Довести пул контента до объёма из GDD и реализовать систему эволюций.

**Задачи:**
- Довести число видов оружия до 15–20 (используя ScriptableObject-паттерн из Этапа 2)
- Реализовать разные типы поведения оружия: melee, projectile, orbit, area, boomerang (см. раздел 5.1 GDD)

- Составить и захардкодить (в данных, не в коде) первую таблицу соответствий оружие→предмет→эволюция для 4–5 пар, чтобы проверить систему end-to-end

**Definition of Done:** Есть минимум 15 оружий, минимум 4–5 рабочих эволюций, которые триггерятся согласно условиям и заметно меняют оружие визуально/по эффекту.

## Этап 5 — Враги: разнообразие и масштабирование сложности

**Цель:** Наполнить бестиарий и выстроить формулу роста сложности от времени забега.

**Задачи:**
- Реализовать 3–5 архетипов поведения врагов (танк/медленный, быстрый/слабый, дальнобойный и т.д.)
- ScriptableObject-описание врагов (статы, поведение, визуал) для лёгкого добавления новых
- Формула масштабирования HP/урона/скорости врагов от прошедшего времени забега — вынести коэффициенты в конфиг для последующей балансировки
- Плотность и частота спавна тоже растут по времени согласно той же логике

**Definition of Done:** Ощутимая разница в сложности между 1-й и 10-й минутой забега, несколько разных силуэтов/паттернов врагов на экране одновременно, без просадки FPS при большом количестве сущностей (см. Этап 9 про профилирование, но базовая пригодность нужна уже тут).

## Этап 6 — Боссы и система алтарей

**Цель:** Реализовать вызов боссов через алтарь, как описано в GDD (боссы не спавнятся автоматически).

**Задачи:**
- Объект "алтарь" на карте (пока можно на фиксированной тестовой позиции, до этапа процедурной генерации)
- Взаимодействие игрока с алтарём (подойти + активировать)
- Спавн босса при активации, с уникальным набором атак/паттерном поведения
- UI-индикация: HP-бар босса, визуальное выделение алтаря на карте/миникарте (если миникарта уже есть, иначе — направляющий индикатор)
- Реализовать минимум одного полноценного босса как референс для дальнейшего наполнения
- **Портал на следующий уровень:** после убийства босса на месте его появления (точка спавна) возникает портал; вход игрока в портал вызывает `ZoneTimer.CompleteZone()` и переводит на следующий уровень. Это единственный способ перехода дальше (фаза духов и таймер переход не открывают)
- Визуальный индикатор портала (направляющая стрелка, если он вне экрана) и запрет повторного вызова босса, пока портал не использован (решить при реализации)

**Definition of Done:** Игрок может завершить забег вообще не встретив босса (если не подошёл к алтарю; тогда он просто выживает против духов как можно дольше), либо найти алтарь, вызвать босса и сразиться с ним; после убийства босса на его месте появляется портал, через который игрок попадает на следующий уровень; бой с боссом ощущается как отдельное событие, а не как ещё один обычный враг.

## Этап 7 — Процедурная генерация карт и множественные миры

**Цель:** Заменить фиксированную тестовую сцену на процедурно генерируемые уровни, добавить структуру миров.

**Задачи:**
- Система процедурной генерации тайловой карты для уровня (алгоритм — на усмотрение реализации: chunk-based генерация вокруг игрока)
- Размещение алтаря босса процедурно на карте (гарантировать достижимость); портал появляется на месте призыва босса, поэтому вокруг алтаря нужна свободная площадка
- Параметризация генерации по миру (тайлсет, препятствия, плотность декораций) через ScriptableObject/конфиг мира
- Реализовать структуру минимум 1 полноценного мира с уникальным тайлсетом и врагами, затем растиражировать паттерн на оставшиеся 2–4 мира из GDD (3–5 миров суммарно)
- Экран выбора мира/уровня (базовый UI, без финальной полировки)

**Definition of Done:** Можно выбрать мир из меню, попасть на процедурно сгенерированную карту этого мира с соответствующим визуалом/врагами/боссом, пройти таймер зоны и отсчёт с духами на этой карте.

## Этап 8 — Мета-прогрессия и сохранения

**Цель:** Реализовать разблокировки между забегами и персистентное сохранение прогресса.

**Задачи:**
- Система сохранения (локальная, PlayerPrefs или файл — выбрать единый подход для всего проекта)
- Хаб/главное меню с экраном персонажей: показ заблокированных/разблокированных, условия разблокировки
- Аналогичный экран для оружия, если оно тоже открывается через мета-прогрессию
- Логика проверки условий разблокировки по итогам забега (например: пройти N уровней, убить конкретного босса, набрать N килов за забег)
- Стартовый набор условий разблокировки для 2–3 дополнительных персонажей как референс

**Definition of Done:** Пройденный забег с выполненным условием реально разблокирует нового персонажа, который сохраняется между запусками игры и доступен для выбора.

## Этап 9 — Оптимизация под мобильные устройства

**Цель:** Обеспечить стабильный FPS на бюджетных Android-устройствах при большом количестве объектов на экране.

**Задачи:**
- Профилирование (Unity Profiler) на пиковых сценариях (максимум врагов/снарядов/партиклов одновременно)
- Полный аудит object pooling (враги, снаряды, гемы, партиклы, любые instantiate/destroy в рантайме)
- Внедрение spatial partitioning (grid) для коллизий, если ещё не сделано в Этапе 1
- Оптимизация батчинга спрайтов (sprite atlases), проверка draw calls
- Тест на реальном или эмулируемом low-end Android устройстве, фиксация целевого FPS (например, 60 на средних устройствах, минимум 30 на low-end)

**Definition of Done:** На целевом low-end устройстве (или его профиле в эмуляторе) игра держит согласованный минимальный FPS в пиковых сценах с духами/боссом.

## Этап 13 — Балансировка и полировка

**Цель:** Довести ощущение игры до финального качества перед релизом v1.

**Задачи:**

- Финальная проверка производительности (повторный профилинг после добавления всего контента)

**Definition of Done:** Игра проходится от начала до конца всеми доступными мирами без критичных багов, ощущается сбалансированной, держит целевой FPS.

## Этап 14 — Подготовка к порту на PC

**Цель:** Заложенный в архитектуре задел (Этап 0 и далее) реализовать как реальную поддержку PC.

**Задачи:**
- Добавить схему управления клавиатура+мышь параллельно джойстику (WASD/стрелки + автоатака остаётся, целиться по-прежнему не нужно)
- Адаптация UI под несенсорный ввод (наведение/клик вместо тапа) и под более широкие экраны/разрешения PC
- Проверка/адаптация под несколько aspect ratio (мобильный ландшафт был фиксирован, PC может требовать больше гибкости)
- Билд под Windows (и опционально Mac/Linux), базовый QA-проход на PC

**Definition of Done:** Игра запускается и полностью играбельна на PC с клавиатурой, без потери функциональности из мобильной версии.

## Примечания по ходу разработки

- Не переходить к следующему этапу, пока не закрыт Definition of Done текущего — это вертикальный, а не горизонтальный план
- Открытые вопросы из раздела 17 GDD (темы миров, таблица эволюций, формулы сложности, конкретные условия разблокировок, список дейликов/ачивок) нужно закрывать непосредственно перед этапом, где они становятся blocking (например, темы миров — перед Этапом 7, список дейликов — перед Этапом 11)
- Архитектурные решения на Этапе 0–2 (ScriptableObject-паттерны, object pooling, структура папок) не менять постфактум без необходимости — на них завязан весь дальнейший контент-пайплайн
